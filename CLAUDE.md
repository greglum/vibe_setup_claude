## Required Startup Workflow

Before doing substantial work, run these checks in order:

1. **Check credentials** — run `echo $SEMOSS_ACCESS_KEY` in the shell to see if the env var is set
   - If empty or unset, tell the user to set their credentials and restart `claude`:
     - **macOS/Linux:** `export SEMOSS_ACCESS_KEY="..." && export SEMOSS_SECRET_KEY="..."`
       (add to `~/.zshrc` or `~/.bashrc` to persist)
     - **Windows PowerShell:** `$env:SEMOSS_ACCESS_KEY="..."` and `$env:SEMOSS_SECRET_KEY="..."`
   - **Stop here** — MCP servers cannot connect without valid credentials.
     The user must set the env vars and restart `claude` so MCP servers reconnect.
   - If the env var has a value, proceed to step 2

2. **Check project config** — read `semoss_config/config.json`
   - If `project_id` is empty, ask the user for their project ID (or offer to create a new SEMOSS project)
   - Persist project metadata once known (`project_id`, `module`, `base_url`, `created_on`)
   - If the user wants a non-default SEMOSS instance, ask which instance to use and update both `semoss_config/config.json` and the URLs in `.mcp.json`

3. **Verify MCP connectivity** — try using one of the SEMOSS MCP tools
   - If MCP servers are not responding, credentials may be invalid — tell the user to check their access key and secret key

4. **Check for client/ directory** — if it does not exist, offer to scaffold the React app (see Scaffolding below)
   - If it exists, check `client/node_modules/` — if missing, run `cd client && pnpm install`

5. **Orient** — list the available MCP tools so the user knows what capabilities are available

## Architecture

Data flow: **Page → Hook → Service → `api.runPixel()` → SEMOSS SDK → Java Reactor → Database**

### Entry Point (`main.tsx`)

```typescript
import { QueryClient, QueryClientProvider } from '@tanstack/react-query'
import { StrictMode } from 'react'
import { createRoot } from 'react-dom/client'
import App from './App'
import './index.css'

const queryClient = new QueryClient({
  defaultOptions: {
    queries: { staleTime: 5 * 60 * 1000 },  // 5 minutes default
  },
})

createRoot(document.getElementById('root')!).render(
  <StrictMode>
    <QueryClientProvider client={queryClient}>
      <App />
    </QueryClientProvider>
  </StrictMode>,
)
```

### App Component (`App.tsx`)

Layer the providers in this order:

1. **ErrorBoundary** — catches React rendering errors
2. **InsightProvider** from `@semoss/sdk-react` — bridges SEMOSS SDK
3. **InsightBridge** — waits for SDK readiness, shows loading/error states
4. **RouterProvider** with `createHashRouter` — hash routing for SEMOSS iframe

```typescript
import { InsightProvider, useInsight } from '@semoss/sdk-react'
import { RouterProvider, createHashRouter } from 'react-router-dom'
import { Suspense, lazy } from 'react'

const Home = lazy(() => import('@/pages/Home'))

const router = createHashRouter([
  { path: '/', element: <Home /> },
])

function InsightBridge() {
  const { insight } = useInsight()
  // Set global insight for api.ts once ready
  // Show loading spinner until SDK initializes
  return <RouterProvider router={router} />
}

export default function App() {
  return (
    <ErrorBoundary>
      <InsightProvider>
        <Suspense fallback={<LoadingSpinner />}>
          <InsightBridge />
        </Suspense>
      </InsightProvider>
    </ErrorBoundary>
  )
}
```

### SEMOSS API Service (`services/api.ts`)

The core bridge between React and SEMOSS. Wraps the SDK's `insight.actions.run()` with typed error handling:

```typescript
let globalInsight: SemossInsight | null = null

export function setGlobalInsight(insight: SemossInsight): void {
  globalInsight = insight
}

export async function runPixel<T>(pixel: string, params?: Record<string, unknown>): Promise<T> {
  if (!globalInsight?.isReady) throw new ApiError('SEMOSS SDK not ready')
  const serialized = serializeParams(params)
  const fullPixel = serialized ? `${pixel}(${serialized})` : pixel
  const response = await globalInsight.actions.run(fullPixel, 'system')
  // Unwrap pixelReturn, check for errors, return typed data
}
```

Key helpers to include: `serializeParams()`, `escapeForPixel()`, `buildFilterParams()`.

### SEMOSS Insight Hook (`hooks/data/useSemossInsight.ts`)

Bridges `@semoss/sdk-react` with `api.ts`:

```typescript
export function useSemossInsight(insight: SemossInsightLike): SemossInsightState {
  // Watch insight.isReady, call setGlobalInsight() once ready
  // Timeout after 15s if SDK never initializes

}
```

### Service Factory Pattern (`services/createService.ts`)

When the user needs CRUD operations, create a service factory:

```typescript
export function createCrudService<T extends { id: number }>(config: {
  reactorName: string
  transform?: (raw: Record<string, unknown>) => T
}) {
  return {
    getAll: (params?) => runPixel<T[]>(`${config.reactorName}GetAll`, params),
    getById: (id) => runPixel<T>(`${config.reactorName}Get`, { id }),
    create: (data) => runPixel<T>(`${config.reactorName}Create`, data),
    update: (data) => runPixel<T>(`${config.reactorName}Update`, data),
    delete: (id) => runPixel<void>(`${config.reactorName}Delete`, { id }),
  }
}
```

Usage:
```typescript
const itemService = createCrudService<Item>({ reactorName: 'Items' })
```

## SEMOSS Platform Concepts

### Pixel Queries

SEMOSS uses a query language called Pixel. Reactors are called as functions:

```
ReactorName(param1=["value1"], param2=[2], param3=[true]);
```

**Array wrapping is required** — all Pixel parameters must be wrapped in `[]`.

### Reactor Naming

Java reactors follow a naming convention: `EntityCRUDReactor` on the Java side, but when called via Pixel, the `Reactor` suffix is stripped:

| Java Class | Pixel Call |
|------------|-----------|
| `ItemsCRUDReactor` | `ItemsCRUD(...)` |
| `GetProjectsReactor` | `GetProjects(...)` |

### Date Field Conventions

| Naming Pattern | Database Type | Example |
|---------------|---------------|---------|
| `*Date`, `*Start`, `*End` | DATE | `startDate`, `endDate` |
| `*At` | TIMESTAMPTZ | `createdAt`, `updatedAt` |

## Code Conventions

### File Organization

- **Path aliases:** Always use `@/*` → `src/*` for imports
- **No barrel files** except `@/types` and `@/services` — barrel files cause circular dependencies
- **Direct imports** for components: `import { Button } from '@/components/ui/button'`
- **Collocate tests** next to source: `Button.tsx` + `Button.test.tsx`

### Naming

- **PascalCase** for components, types, interfaces
- **camelCase** for variables, functions, hooks
- **Boolean prefix:** `is`, `has`, `should` (e.g., `isLoading`, `hasError`)
- **Hook prefix:** `use` (e.g., `useItems`, `useFormModal`)

### TypeScript Rules

- **Strict mode** always enabled
- **`function` keyword** for top-level exported functions (not `const` arrow)
- **Explicit return types** on exported hooks and utility functions
- **No return type** on React components (inferred is fine)
- **Explicit Props types** — define and export `interface FooProps { ... }`
- **No nested ternaries** — use `if`/`else` or early returns
- **No `any`** — use `unknown` and narrow

### Styling

- **Tailwind CSS only** — no inline styles, no CSS modules, no styled-components
- **Use `cn()` helper** for conditional classes
- **CSS variables** for theme tokens (colors, spacing, radii)
- **No hardcoded hex colors** in JSX — use Tailwind classes or CSS variables

### React Patterns

- **TanStack Query** for all server state — never `useEffect` + `useState` for data fetching
- **`createHashRouter`** — required for SEMOSS iframe embedding. Never use `createBrowserRouter`.
- **Lazy-load pages** with `React.lazy()` + `<Suspense>`
- **Error boundaries** around route-level components
- **FormField components** for form inputs — wrap each input with label, error display, description

### Component Structure

When creating UI components, follow this order:

```typescript
// 1. Imports
import { cn } from '@/utils/cn'

// 2. Types
interface ButtonProps { ... }

// 3. Component
export function Button({ className, ...props }: ButtonProps) {
  return <button className={cn('...', className)} {...props} />
}
```

## MCP Configuration

Claude Code reads `.mcp.json` from the project root automatically. This file uses
`${env:SEMOSS_ACCESS_KEY}` and `${env:SEMOSS_SECRET_KEY}` references that Claude Code
resolves from environment variables at MCP server startup.

**If MCP servers fail to connect**, the most common cause is missing environment variables.
Tell the user to set them and restart `claude` — MCP servers only read config at startup.

Do NOT write literal credentials into `.mcp.json` — the env var approach keeps secrets out of git.

Three SEMOSS MCP servers are configured:

| Server | Purpose |
|--------|---------|
| `Semoss_Platform_Instructions` | Platform documentation and guidance |
| `Semoss_project_manager` | Project management — create, list, upload, publish |
| `Semoss_database_helper` | Database operations — create, query, schema |

## Database Rules

If a task involves a database:

1. Ask the user to create the database or provide the database ID
2. After receiving the ID, call `get_schema(database_id)` via the MCP tools
3. The returned schema is Base64-encoded — decode it before use
4. Write the decoded schema into `semoss_config/` for reference

Example Base64 helper:

```python
import base64
from pathlib import Path

encoded = Path("schema.b64").read_text()
decoded = base64.b64decode(encoded).decode("utf-8")
Path("semoss_config/schema.sql").write_text(decoded)
```

When creating temporary Base64 files:
- Put them under a `temp/` directory
- Mirror the source directory structure
- Delete them after use if no longer needed

## Adding a New Entity (Checklist)

When the user wants to add a new data entity to the app:

1. **Database** — Define the table schema (if database-backed)

## Common Pitfalls

- **Forgetting to publish** — Uploaded files are not visible until the project is published
- **Overwriting without backup** — Always check for existing remote files before upload; use the asset sync script which handles backups automatically
- **Stale credentials** — If MCP tools stop working, check that `SEMOSS_ACCESS_KEY` and `SEMOSS_SECRET_KEY` env vars are still valid
- **Wrong module path** — `api_module_url` (for API calls) and `web_module_url` (for user-facing URLs) are different paths
- **Base64 schema** — Database schemas from `get_schema()` are Base64-encoded; decode before use
- **npm/yarn usage** — Always use pnpm. The `preinstall` script enforces this.
- **Forgetting to build** — Run `pnpm run build` before uploading to SEMOSS. The `portals/` directory is build output, not source.
- **Wrong Vite base path** — Must be `'./'` (relative). Absolute paths break in SEMOSS iframes.
- **Browser history routing** — Never use `createBrowserRouter`. SEMOSS portal viewer requires hash routing.
- **Barrel file imports** — Only use barrel exports from `@/types` and `@/services`. Elsewhere, import directly to avoid circular dependencies.
- **Pixel array wrapping** — All Pixel parameters must be wrapped in `[]`: `param=["value"]`, not `param="value"`
- **Closing Java connections** — Never close `Connection` objects in SEMOSS reactors. SEMOSS manages the connection lifecycle.
- **Data fetching with useEffect** — Use TanStack Query hooks, never `useEffect` + `useState` for API calls.
- **Hardcoded colors** — Use Tailwind classes or CSS variables, never hex values in JSX.
